# Documentation site generator — which tool builds the docs site (M11b)

## 1. The question

Roadmap P-6 and M11b name an MkDocs site (`mkdocs-material`) and an exit of `mkdocs build
--strict`. Planning M11b found that choice ageing: mkdocs-material 9.8.0 (2026-10-24) announces
its end of life on **2027-05-05**, with critical fixes until then, and MkDocs itself hasn't
released since 1.6.1 (2024-08-30). Its successor from the same team, Zensical, reads `mkdocs.yml`
but is alpha (0.0.73). Oleksii asked for this comparison before the plan picks a tool, weighing
long-term support and UI/UX, with mdBook as the first candidate.

What the site has to carry (roadmap §4 M11b): architecture pages with diagrams, a REST API
reference rendered from the OpenAPI document, a configuration reference generated by `xtask`,
deployment pages, operator runbooks. What the build has to catch: a link to a missing page or a
missing anchor (the exit's "strict" build).

## 2. Candidates and maintenance signals

Measured 2026-10-29 from npm, PyPI, crates.io and the GitHub API.

| Tool | Version | Stack | Releases, last 12 months | Notes |
|---|---|---|---|---|
| mdBook | 0.5.4 (2026-07-06) | Rust, one binary | 6 | `rust-lang/mdBook`, the Rust project's own; 22k stars |
| Starlight | 0.42.7 (2026-10-23), Astro 7.4.4 | Node | 49 (the monorepo's packages) | `withastro/starlight`, the Astro core team; pre-1.0, so a minor version can break config |

## 3. The spike

One generator (`gen.py`, kept in the session scratchpad with the sites) wrote the same pages in
each tool's dialect, from this repository's own material:

- an index;
- an architecture page with two Mermaid diagrams (a flowchart of a change's path, a sequence of
  a lease hand-off) and a callout;
- a configuration reference: a YAML example, a warning callout, and a table of all 116 V-rules
  generated from `data_avalanche_config::RULES`;
- a management API reference generated from the real `openapi()` document (16 routes, grouped
  by tag: summary, minimum role, parameters, statuses);
- a runbook ("a halted table") with tip and warning callouts and PostgreSQL/MySQL tabs.

Each site was built from a clean scratch project with the tool's documented minimal config, then
built again with one more page linking to a missing page and to a missing anchor. The built
sites were served locally and captured with headless Chrome (architecture, config reference and
runbook pages; a dark-scheme and a 390 px-wide capture of the architecture page).

## 4. Results

| | mdBook | Starlight | Docusaurus | VitePress | mkdocs-material | Zensical |
|---|---|---|---|---|---|---|
| Build, 6 pages | **0.1 s** | 7.2 s | 63 s | 15.4 s | 1.9 s | 1.5 s |
| Toolchain installed | **17 MB** (2 binaries) | 437 MB | 997 MB | 280 MB | 213 MB (venv, both) | (same venv) |
| Missing page fails the build | **no** (exit 0, link left dangling) | yes (plugin) | yes | yes | yes (`--strict` + `validation`) | yes (`--strict`) |
| Missing anchor fails the build | **no** | yes (plugin) | yes (`onBrokenAnchors`) | **no** (exit 0) | yes | yes |
| Search built in | yes (elasticlunr) | yes (Pagefind) | **no** (Algolia, or a community plugin) | yes (MiniSearch) | yes | yes |
| Mermaid | third-party preprocessor, client-side; warns it was built for mdBook 0.5.0 | plugin, client-side | official theme | plugin | built in, loads `mermaid` from unpkg at view time | built in, loads it from unpkg |
| Callouts | GitHub `> [!NOTE]` (built in since 0.5) | `:::note` | `:::note` | `::: tip` | `!!! note` | `!!! note` |
| Tabs | **none** (a preprocessor would be another third-party dependency) | `<Tabs>` (MDX page) | `<Tabs>` (MDX) | code groups only | `=== "Tab"` | `=== "Tab"` |
| Generated text | raw `<value>` in a rule's text: a warning, the HTML passed through | `.mdx` pages: `{`, `}`, `<` must be escaped; `.md` pages are plain Markdown | every page is MDX: the same escaping | Vue templates: `{{` must be escaped | plain Markdown | plain Markdown |
| Output size | 3.9 MB | 6.2 MB | 5.7 MB | 4.7 MB | 2.7 MB | 0.7 MB |

The generated rule texts had to be entity-escaped (`&lt;`, `&#123;`, …) before the MDX tools would
build at all; `xtask` would do the same for every generated page.

**UI/UX, from the captures:**

- **mdBook**: the classic book layout (a numbered chapter sidebar, prev/next arrows, a theme
  picker). No right-hand table of contents. The wide V-rule table renders badly: the last column
  is squeezed to a word per line while the others stay wide. The look is serviceable but dated
  beside the others.
- **Starlight**: the most finished look of the six: a sidebar, a right-hand "On this page", a
  search box with a shortcut, light/dark/auto. Its asides are coloured and titled; the tabs and
  the wide table render cleanly; the Mermaid diagrams follow the theme.
- **Docusaurus**: clean and familiar (breadcrumbs, a right-hand table of contents), the light
  theme by default; with no search box unless one is added.
- **VitePress**: close to Starlight's layout, compact and fast to read; no tabs for prose.
- **mkdocs-material / Zensical**: the Material layout (a header search, a right-hand table of
  contents, the best tabs and admonitions); Zensical's default theme is the more modern of the two.

Each layout collapses to a single column at phone width. In the 390 px captures the wide
flowchart and the wide table seemed to run past the edge in every tool, but that was the capture:
headless Chrome lays a page out at least 500 px wide whatever its window (measured during M11b's
planning: `innerWidth` 500 at `--window-size=390`), so a 390 px screenshot clips it. At a true
500 px the Starlight site of M11b keeps its width once each wide table scrolls in its own box (a
few lines of CSS), and its flowcharts run top to bottom.

## 5. Findings by tool

- **mdBook.** The lightest and fastest by far, and the Rust project's own. But the build checks
  nothing: a missing page or anchor ships as a dead link, so a strict build means a separate link
  checker (`lychee`, or an `xtask` check over the built HTML). No tabs, and Mermaid through a
  third-party preprocessor that already trails mdBook's version. Wide reference tables render
  poorly. Its strength is stability: the book format has changed little in years.
- **Starlight.** Everything the site needs without custom code: search, asides, tabs, link and
  anchor validation, light and dark themes. The risks are that it is pre-1.0 (its config has
  changed between minor versions) and that it brings Node: about 440 MB in CI, cached. Generated
  pages stay plain `.md`, which avoids MDX escaping; only hand-written pages that use components
  are `.mdx`.
- **Docusaurus.** The most widely used, and a strict link and anchor check. But it is the heaviest
  (1 GB, a 63 s build for six pages), every page is MDX, and it has no built-in local search.
- **VitePress.** Fast and pleasant, but the stable line hasn't released since 2025-08 while 2.0
  stays in alpha, and a missing anchor passes the build.
- **mkdocs-material.** It still works well, and its strict build checks both pages and anchors.
  But it reaches end of life on 2027-05-05, on an MkDocs core that has stopped releasing.
- **Zensical.** The same content and `mkdocs.yml` built unchanged, with the strictest and
  clearest diagnostics (both broken links reported with their source lines), the smallest output,
  and an active team. But it is alpha: 70 releases in a year means its behaviour moves under the
  site.

## 6. Recommendation

**Starlight**, pinned (Astro and Starlight by exact version, `package-lock.json` committed), with
`starlight-links-validator` making the build fail on a missing page or anchor:

- It is the one tool that meets every requirement with no custom code, and it has the best UI/UX
  of the six.
- Its maintenance is the most active of the stable choices.
- The content stays portable: generated pages are plain Markdown, and only the runbooks' tabs are
  MDX components.

The cost is a Node toolchain in CI and one `npm ci` for a contributor who builds the site.

**Runner-up: mdBook**, if a Rust-only toolchain matters more than the UI. It would then need:

- a link and anchor checker of our own in `xtask`, run over the built HTML;
- no tabs (one section per source instead);
- the third-party Mermaid preprocessor.

**Watch: Zensical.** At its 1.0 it would be the natural home for a Material-style site, and the
spike showed today's `mkdocs.yml` moving to it unchanged. Not before then.

**Not recommended:**
- mkdocs-material (end of life 2027-05);
- Docusaurus (its weight, and no local search);
- VitePress (its stalled stable line, and no anchor check).

**What changes in the roadmap if Starlight is chosen:**
- P-6 and §4 M11b: "an Astro Starlight site" in place of "MkDocs";
- M11b's exit: "the site builds with its link validation" in place of `mkdocs build --strict`;
- §2's layout: `docs/` keeps the site, with `astro.config.mjs` and `package.json` beside its
  pages, not `mkdocs.yml` at the repository's root.

The choice is recorded as Q-M11b-1.

## 7. Reproducing

The spike lives in the session scratchpad (`ssg/`):
- `gen.py <scratch> <tool> <out> [--broken]` writes the pages;
- `sites/<tool>/` holds each project;
- `shots.py` serves the built sites and captures them;
- `shots/sheet-*.png` tiles the captures.

The commands, per tool:
- `mdbook build`;
- `npx astro build`;
- `npx docusaurus build`;
- `npx vitepress build docs`;
- `mkdocs build --strict`;
- `zensical build --strict`.
