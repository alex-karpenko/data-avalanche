# 1.0.1 — Dependency refresh Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Release `1.0.1` with every dependency at its newest stable version (or held, in writing, with
the reason), and make that refresh a gate every later release passes.

**Architecture:** Tasks 1–5 move each kind of dependency (toolchain and compatible crates; deltalake; the
API-breaking crates; CI tools and test images; the documentation site), each proven by the suites
that exercise it. Tasks 6–7 add `cargo xtask deps [--check]`, which compares everything the
repository pins against its registry and against `dependency-exceptions.yaml`, and make
`release.yml` refuse a tag while it fails. Tasks 8–9 bump the version and re-run the acceptance
evidence that a new Delta engine can move.

**Tech Stack:** Rust 1.100.0; deltalake 1.1.2 / deltalake-core 1.1.4; pgwire-replication 0.5.0;
serde-saphyr 2.1.1; sqlparser 0.64.0; prometheus-client 0.26.0; reqwest (blocking) in `xtask`.

**Spec:** No product spec changes: 1.0.1 changes no configuration key, API, metric name, halt code or
on-disk format. The requirement is Oleksii's (2026-11-13): "update all used dependencies to the
last stable versions and make this a mandatory rule for each future release", with the rule as
played back and confirmed — every release takes the newest stable version of everything; where a
newer one can't be used, the exception is written down with its reason and re-checked at the next
release. The survey and the scratch verification behind this plan are in "Evidence" below.

## Global Constraints

- `main` is off limits; branch `feat/claude/v1.0.1-deps-refresh`; one PR; Oleksii merges.
- Quality gates before every commit: `cargo fmt --all --check`,
  `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`.
- Exact pins stay exact (`=x.y.z`) where they are today; they move to the new exact version.
- One arrow major workspace-wide (D-MS.14): arrow stays at the major deltalake resolves.
- Historical plans (`doc/v1.0/M*.md`) and frozen probes (`prototypes/`) are not edited to new
  versions: they record what was true when written. Only living docs change.
- No credentials or key paths in output, code or docs; Oleksii runs credentialed commands with `!`.
- Commit trailer: `Claude-Session: https://claude.ai/code/session_01DNsmZ8HoPeX5XCQzNa57CM`.

## Review Focus

1. **A newer release lands between the PR's green run and the tag.** The tag's `release.yml` fails at
   `deps --check`, naming the item, its newest version and the two fixes (bump, or hold with a
   reason). Pinned by Task 6's `a_behind_dependency_fails_with_its_newest_version_named` and the
   README checklist (Task 7).
2. **A registry can't be reached or rate-limits.** The check fails closed (`unknown: <error>`), never
   passes an item it couldn't look up. Task 6: `a_lookup_failure_fails_the_check`.
3. **Version order is numeric, prereleases don't count.** `1.100.0 > 1.99.1`, `v10 > v9`,
   `2.40.2 > 2.9.0`; `1.0.6-beta`, `-rc.1`, `-alpha` are never "newest". Task 6:
   `newest_of_shape_compares_numerically`, `newest_of_shape_skips_other_shapes_and_prereleases`.
4. **An exception outlives its reason.** A held item that has caught up, or an exception that names
   nothing in the inventory, fails the check, so the list can't rot. Task 6:
   `an_exception_for_a_current_dependency_is_stale`, `an_exception_for_nothing_is_stale`.
5. **deltalake 1.1's MERGE planner changes cost or lag.** It prunes target files differently (streamed
   MERGE early filter, roaring-bitmap duplicate tracking). Task 9 re-runs bench and chaos on both
   sources against D-V1.3 and the 1.0.0 figures, and updates the published cost figures if they move.

## Decisions and rulings

- **D-R1 Scope** (my call, from the confirmed inventory): everything the product builds or tests with —
  direct Rust dependencies of every workspace member and `xtask` (normal, dev, build), the toolchain,
  the image's build base, the Actions and the tool versions workflows pin (Helm), the `test-infra`
  tool images, DuckDB, the docs site's npm packages and Node LTS. Transitive crates are refreshed by
  `cargo update` (newest compatible with their dependents). **Out:** the database images (they are the
  source support matrix; adding MariaDB 12.3/13.0 or MySQL 9.7/26.x is a feature), `prototypes/`
  (frozen evidence, own lockfiles), runner labels (`ubuntu-24.04`).
- **D-R2 "Newest stable"** per registry: crates.io `max_stable_version`; the Rust stable channel; an
  image's highest tag of the same shape as the pinned one (no prerelease words); an Action's latest
  release compared at the ref's precision (`@v7` → major, `@v10.2.0` → exact); npm `latest`; PyPI
  `info.version`; Node's newest LTS major. A tag with no digits (`nonroot`) is floating: always
  newest, reported, never behind.
- **D-R3 Exceptions** live in `dependency-exceptions.yaml` at the repository root: `kind`, `name`,
  `held` (the version it's held at, or `"*"` for "out of scope by design"), `reason`. A held entry
  that has caught up, or that matches nothing, fails the check. `"*"` entries never go stale.
- **D-R4 The gate is the release.** `release.yml`'s `version` job runs `cargo xtask deps --check`
  before anything builds; a manual dispatch runs it too (a dry run). PR CI doesn't run it: an
  upstream release would turn every open PR red.
- **D-R5 Version `1.0.1`, a patch:** no operator-visible change beyond dependencies. The release
  notes come from `--generate-notes` (the PR).
- **D-R6 What a refresh must pass** (written into the README checklist): hermetic suite; full
  integration and E2E on both sources (CI's MySQL/MariaDB matrix); k3s; `cloud.yml` on S3, GCS and
  Azure; and, when the Delta engine or a source transport moves, `cargo xtask bench` and `chaos` on
  both sources. The 24-hour soak is not re-run for 1.0.1 (my call: no product code changed beyond two
  renames; Oleksii can ask for it).
- **D-R7 The rule's text** goes into `CLAUDE.md` (Implementation workflow) in this PR, since this plan
  creates it; `CLAUDE.md` otherwise takes its own PR.
