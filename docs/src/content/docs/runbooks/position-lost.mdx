A pipeline resumes from its checkpoint: a position in the source's log. When the source can no
longer serve that position, the changes in between are gone, and the only way to a correct table
is a fresh copy. Depending on its settings the pipeline starts again from the server's position
now by itself, or stops in `error` for you to decide.

Whether it then copies the tables follows `snapshots.mode`. With `initial` or `always` it copies
every table. With `never`, the default, it takes no snapshot: it streams on, the log warns that
the changes before now are missing, and you copy the tables yourself with a
[snapshot job](/data-avalanche/runbooks/snapshot-jobs/) for each table the gap touched.

:::caution[A fresh copy keeps rows deleted in the gap]
The copy upserts every row it reads and deletes nothing: a row deleted at the source during the
gap stays in the Delta table. When the tables must be exact, copy them with a snapshot job asked
with `"truncate": true`, which empties each Delta table before its copy.
:::

## The WAL a slot holds grows

**Symptom:** `DataAvalancheWalLag`, a growing `data_avalanche_wal_lag_bytes`, the server's disk
filling.

The slot holds the WAL from the pipeline's last checkpoint. It grows while the pipeline is stopped,
paused, failing to commit, or far behind.

1. Check the pipeline: `GET /v1/pipelines/<id>`. A stopped or paused pipeline still holds its slot;
   resume it, or remove it from the config if it's gone for good (the slot is dropped with it,
   with `auto_cleanup: true`).
2. A pipeline that runs but doesn't keep up: look at `data_avalanche_sink_commit_failures_total`
   (the storage) and `data_avalanche_flush_duration_seconds` (the MERGE cost).
3. With `max_wal_lag_bytes` set, a pipeline past it stops in `error` and keeps its slot. Fix the
   cause, then `POST /v1/pipelines/<id>/restart`.

## The slot is gone or invalidated

A slot past `max_slot_wal_keep_size` is invalidated by the server; a slot can also be dropped by
hand, or advanced past the pipeline's checkpoint.

- With `slot_management: managed` (the default) the pipeline creates the slot again at its next
  start and streams from the new slot. It copies the tables as `snapshots.mode` says: under
  `never` it takes none, and warns. The log says why.
- With `require_existing` the pipeline stops in `error`: it creates no slot. Have the DBA create
  the slot again. A slot made again starts at the server's position now, past the pipeline's
  checkpoint, so the changes in between are lost and the pipeline refuses it with
  `slot_on_orphan: halt` (the default). Set `slot_on_orphan: adopt_resnapshot` (applied without a
  restart) and `POST /v1/pipelines/<id>/restart`: the pipeline adopts the slot and copies the
  tables as `snapshots.mode` says. Once it runs, set `slot_on_orphan` back to `halt`.

## A failover (`WAL_SOURCE_CHANGED`)

**A failover slot carries the stream over.** On PostgreSQL 17 and later, a slot the pipeline
manages (`slot_management: managed`) is a failover slot. When the standby streams from the
primary through a physical slot (`primary_slot_name`), with `dbname` in its `primary_conninfo`,
`sync_replication_slots` on and `hot_standby_feedback` on, and the primary names that physical
slot in `synchronized_standby_slots`, the standby keeps a copy of the pipeline's slot. A promotion that
copy followed continues the stream on the new timeline, with no halt and no copy, under either
`source_change_action`: the copy must have confirmed exactly the pipeline's checkpoint, and no
Delta table's marker may be past it. That holds whether the pipeline was running (its reconnect to
the promoted server starts it again, and the start continues) or stopped. The log warns, naming
both servers, that the slot `came over synchronized up to the checkpoint, with no marker of the
lake past it, so the stream continues on the new timeline`, and the checkpoint records the new
server. Otherwise everything below applies. A slot made before PostgreSQL 17, a standby that
doesn't sync slots, and a promotion whose copy is behind or past the checkpoint aren't covered.
Under `require_existing` the DBA's slot is carried over only when it was created as a failover
slot (`pg_create_logical_replication_slot('<slot>', 'pgoutput', false, false, true)`).

- **Plan the switchover.** The standby copies the slot from time to time, not at each of the
  pipeline's acknowledgements. After a crash under load its copy usually lags the last one, and
  the start halts as below (or re-snapshots under `re_snapshot`). A planned switchover continues
  reliably: stop the writes to the primary, let the pipeline catch up, wait until the standby's copy
  (`SELECT confirmed_flush_lsn, synced FROM pg_replication_slots` on the standby) shows the
  primary's `confirmed_flush_lsn`, then promote.
- **A down standby stalls the pipeline.** On PostgreSQL 17 and later the primary holds a failover
  slot's changes back until every standby named in `synchronized_standby_slots` has received
  them. A standby that is down or far behind stops the pipeline's stream: its lag grows, and only
  the server's log says why. Take the standby out of `synchronized_standby_slots` while it's down.
- **A slot made before an upgrade to 17** stays a plain slot: the pipeline makes a failover slot
  only when it creates one, so such a slot isn't carried over.

**Symptom:** after a failover, or after the host was pointed at another server, the pipeline stops
in `error` with `WAL_SOURCE_CHANGED`, naming the server its checkpoint was read on and the one it
reads now.

The checkpoint records the server: its system identifier and its timeline. A promoted replica
keeps the identifier and moves to a new timeline. Its WAL ends where its replication did, which can
be behind what the lake already holds, so it writes again LSNs the lake has marked. Resuming would
skip those changes. Unless a standby synchronized it (above), the logical slot isn't on the
promoted server either: PostgreSQL doesn't copy a plain slot to a physical replica. The check runs
at a start and at every stream reconnect, before the pipeline drops or makes a slot on the server
it reaches. A reconnect that reaches a promoted server of the same system starts the pipeline
again, whose start continues the stream (above) or halts; one that reaches any other server halts
the running pipeline at once, rather than replacing the lost slot there. Under `re_snapshot` the
pipeline starts again, as at a restart, and recovers as in step 2.

1. If the old server is the one you want, point the pipeline back at it (a reload restarts the
   pipeline) and it resumes.
2. Otherwise set `source.postgres.source_change_action: re_snapshot` (a reload applies it, without
   a restart) and `POST /v1/pipelines/<id>/restart`. The pipeline moves every Delta table under
   the sink's prefix onto the new server's position (a job's copy, and a table no longer in the
   config, included), makes its slot there (under `require_existing`, have the DBA create it
   first), and copies the tables as `snapshots.mode` says: under `never`, none, with a warning, and
   you start a snapshot job for each table. A Delta table that refuses the move halts
   `SINK_REJECTED` and the others go on (see
   [A halted table](/data-avalanche/runbooks/halted-table/)).
3. Rows the old server wrote that the promoted one never received (the changes written after the
   replica fell behind or was cut off) stay in the Delta tables. The copy only upserts, so it
   doesn't delete them; they are the changes the failover lost. To start clean, copy the tables
   with a snapshot job asked with `"truncate": true`, as in the caution above and in
   [A halted table](/data-avalanche/runbooks/halted-table/#3-copy-the-table-again).

Leave `source_change_action` at `re_snapshot` only where a failover should recover by itself.

If the pipeline's address reaches more than one server, the runs keep finding another one. Under
`re_snapshot` each such run starts the pipeline again, and three runs in a row that each find
another server and make no checkpoint durable stop the pipeline in `error`, as for a changing
binlog server (see the MySQL and MariaDB tab), usually with `WAL_SOURCE_CHANGED`. Reconnects that
keep reaching a promoted server of the same system do the same under either action, and that halt
carries no code: look for "the source's address reaches more than one server" in its reason.

## A renamed or dropped publication

The pipeline finds its publication by name at each start. Under `managed` a publication it can't
find is created again, with the pipeline's tables, and the pipeline re-snapshots: the WAL since its
checkpoint was decoded without it. The renamed publication stays behind; drop it. Under
`require_existing` the pipeline stops in `error` ("publication … doesn't exist"): rename it back,
or set `source.postgres.publication` to the new name and reload.

## An orphan slot

The slot exists, but the pipeline has no state: its state location was lost or moved, or a new
pipeline took an old slot's name. With `slot_on_orphan: halt` (the default) the pipeline refuses to
start. Then either:

- under `managed`, drop the slot, for a first start (the pipeline creates it, and copies the
  tables as `snapshots.mode` says). Under `require_existing` this fails: with no state and no slot
  the pipeline refuses to start;
- restore the pipeline's state location, if it was lost by mistake;
- or set `slot_on_orphan: adopt_resnapshot`: the pipeline takes the slot over, moves it to the
  current WAL position and copies the tables as `snapshots.mode` says (none under `never`, with a
  warning). `slot_on_orphan` is applied without a restart, so restart a pipeline in `error` with
  `POST /v1/pipelines/<id>/restart`.

## The binlog was purged

**Symptom:** the pipeline stops in `error`, its reason saying the server purged the binlog it
needs. A pipeline stopped for longer than the server keeps its binlog
(`binlog_expire_logs_seconds`) meets this when it starts again.

- With `binlog_purge_action: error` (the default) the pipeline waits for you. To copy afresh, set
  `binlog_purge_action: re_snapshot` (a reload applies it, without a restart) and restart the
  pipeline: it streams from the server's position now and copies the tables as `snapshots.mode`
  says.
- With `re_snapshot` it does that by itself, with a warning. Under `snapshots.mode: never` no copy
  follows: start a snapshot job.

## The server changed (`BINLOG_SOURCE_CHANGED`)

With `replication_type: binlog`, a position is a file and an offset of one server. When the host
now leads to another server (a failover, a restore), the checkpoint means nothing there. The
pipeline tells servers apart by `server_uuid` on MySQL and by `server_id` on MariaDB. On MariaDB it
also checks that the position is an event boundary of a binlog file the server holds
(`BINLOG_GTID_POS`). And a checkpoint whose file the server never held is another server's, not a
purge: the file has another base name, or comes after the server's newest binlog. A file older
than the server's oldest is a purge (see above). The same checks run when the pipeline
reconnects, not only at a start.

- With `binlog_purge_action: error` (the default) the pipeline stops in `error` with
  `BINLOG_SOURCE_CHANGED`. Point it back at its server, or recover as below.
- With `binlog_purge_action: re_snapshot` the pipeline starts from the new server's position, with
  a warning, and copies the tables as `snapshots.mode` says. Found at a reconnect, the pipeline
  runs its start again to do so. To recover a stopped pipeline, set it (a reload applies it,
  without a restart) and `POST /v1/pipelines/<id>/restart`.

**A server that keeps changing.** Under `re_snapshot` a run that finds another server ends and the
pipeline starts again. Three runs in a row that each find another server than the run before, none
making a checkpoint durable, stop the pipeline in `error` with
`BINLOG_SOURCE_CHANGED` (on PostgreSQL, `WAL_SOURCE_CHANGED`), saying that the source's address
reaches more than one server (a load balancer, or a DNS name over several). Point the pipeline
at one server (no load balancer, no round-robin DNS name), then stop and resume it. The count
starts again when a run makes a checkpoint durable or ends for another reason, and when the
pipeline is stopped. It doesn't decay with time: on a source that writes nothing in between, three
genuine failovers in a row, however far apart, can stop the pipeline the same way; stop and resume
it.

Two cases aren't caught. On MariaDB: another server with the same `server_id` and the same binlog
file names, whose file happens to have an event boundary at the checkpoint's offset. On MySQL: a
copy of the server with the same `server_uuid` and the same file names. Prefer GTIDs: with
`replication_type: gtid` (the server needs them on) a position survives a failover to a replica,
and none of the above applies. Switching is a reload: the pipeline can't carry a file position
over to a GTID one, so it starts from the server's position now (with
`binlog_purge_action: re_snapshot`) and copies the tables as `snapshots.mode` says.
